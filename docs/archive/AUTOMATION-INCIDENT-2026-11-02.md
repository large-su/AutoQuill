## 现场与处置

用户早上仅将全链路撰写从每天 10 篇改为 2 篇，发布仍为每天 9 篇，希望逐步消耗存稿。这是正常配置操作，不能触发批量连发。

07:54:27/28 的计划保存日志确认 `full_chain=2`、`publish_drafts=9`。本机台账确认 8 次成功发布：07:30:23–07:31:00 一次，09:09:38–09:13:55 连续七次。用户观察约十篇，但本机证据只确认八篇，不将另外两篇当作已验证事实。相同任务键 `auto:2026-11-02:publish_drafts:slot:0` 出现 234 条生命周期记录；草稿发空后继续空跑至 09:52。现场站点缓存也显示当天已发布 8、草稿 0。

用户已在 09:52 暂停；排查开始再次确认暂停、无在途 worker，并备份计划、日状态、原始台账、演进记录和 API 状态到忽略目录 `logs/incident-1102-before/`。排查和回归均使用临时目录与模拟执行器，没有再调用真实发布。已经发布的内容未自动删除或再次改动。安装修复前关闭自动化总开关，避免重启恢复运行；交付保持停用，发布 9 / 撰写 2 的配额原样保留。

## 可重复的因果链

1. 原排班的发布 `slot:0` 已完成。修改写作配额使整个计划指纹变化。
2. `materialize_day` 保留已完成项，但 `_build_schedule` 将剩余发布从编号 0 重新生成，产生同名已完成项和待执行项。
3. 调度器按 key 绑定当天记录时选中第一条已完成项，重新将它设为运行；另一条到期的同名待执行项仍保留。
4. 每个 tick 都再次选中同名待执行项。原执行入口没有完成状态、实际完成时间间隔的硬检查，因此不断发布下一篇草稿。
5. 后续空草稿结果覆盖了同 key 的日状态。日状态中 `counters` 未跟随台账更新，界面显示的已完成数失真，但原始追加台账中的八次成功并未丢失。配额 9 尚未达到，也无法阻止配额内的集中连发。

隔离命令 `.venv/Scripts/python.exe -m unittest -v tests.test_automation_quota_replan` 在修复前发现重排后 13 个任务只有 12 个唯一 key；真实调度生命周期的最小复现还出现同一 key 在 37 秒后再次调用模拟发布器。红灯记录位于 `logs/incident-1102-repro-red.txt`、`logs/incident-1102-primary-red.txt`。这不是单次批量发布功能，而是同一时隙被反复消费。

## 修复机制

- 重排的剩余槽位从已消耗数量之后编号，并避开保留记录的 key；实际完成时间作为后续排班与补做间隔的锚点。
- 日状态随当前台账同步计数；界面完成数采用不低于该证据的值。演练记录不占真实配额。
- 旧重复记录归并为唯一执行项，重复原件保留在 `recovered_duplicates`。成功台账恢复被后续失败/空草稿覆盖的状态，原始台账文件不改写。
- 执行前再次拒绝已完成、已领取或重新推迟的任务；发布按当天真实计数和上次实际成功完成时间检查配额、间隔。手动立即发布也不能绕过这两项，演练不产生真实发布。
- 领取状态写入后回读校验，无法持久化时暂停，不调用外部执行器。

真实事故的日文件和完整台账复制到临时目录后，重放得到：成功数 8、重复项恢复 1、唯一待发布槽位为 `slot:8`，10:00 不调用发布器；记录见 `logs/incident-1102-replay.json`。测试还覆盖同类型不同 key 的最小间隔、重启恢复、已满配额、手动入口及状态保存失败，避免只验证排班数组而遗漏执行链路。
