# 提交、打包与 Release 发布规范

| 项目 | 内容 |
|---|---|
| **适用版本** | v5.0.7 起 |
| **最后更新** | 2026-10-10 |
| **状态** | 活跃 |
| **说明** | 所有 Agent 与维护者执行发布时遵循的固定步骤、验证分级和完成标准 |

用户授权发布后，按本文件完成准备、提交、构建、上传和校验。统一入口是 `tools/release.py`；固定工作由脚本执行，源码调查和额外验证由实际改动决定。

## 1. 普通小版本：五步执行

| 步骤 | 操作 | 完成标准 |
|---|---|---|
| 1. 准备版本 | 修改 `core/version.py`，补充本版 CHANGELOG | 版本高于上一版，变更描述对应实际改动 |
| 2. 准备说明 | 写 `release/release_notes_<版本>.md` 和 UTF-8 的 `logs/release-commit.txt` | 说明文件存在，提交摘要讲清本版行为 |
| 3. 核对计划 | 查看 `git status --short`、`git diff --stat`，运行 `--plan` | 文件范围、测试选择和两个资产名称正确 |
| 4. 发布 | 执行下方发布命令一次 | 相关检查通过，版本提交、构建、原子推送和 Release 创建成功 |
| 5. 核对结果 | 查看脚本校验结果，查询本次提交的 CI 状态一次 | 资产一致、工作区干净；报告链接、提交、测试、耗时及真实 CI 状态 |

在仓库根目录执行：

```powershell
$env:PYTHONIOENCODING='utf-8'
.venv\Scripts\python.exe tools\release.py --plan
.venv\Scripts\python.exe tools\release.py --message-file logs\release-commit.txt
```

发布说明默认读取 `release/release_notes_<版本>.md`，不同路径用 `--notes` 指定。
脚本会在提交前同步 README、安装器版本和近期演进历史，运行一次检查，提交一次、构建一次，推送 `main` 与本次 tag，再创建并校验 Release。演进历史通过本机 Git 生成，不增加网络请求或全量测试步骤。

执行日志可保存到 `logs/release-<版本>.log`；脚本输出阶段耗时和总耗时，测试与构建详细日志自动存到 `logs/`。成功时读取摘要，失败时读取相应日志的异常段。

## 2. Git、版本与资产约定

- 版本唯一来源是 `core/version.py`；tag 为 `v<版本>`。
- 第一位（主版本）表示软件的大进化节点，仅在用户明确要求时修改。
- 第二位（次版本）用于用户授权的自主探索、升级进化；递增后第三位归零。
- 第三位（修订版本）用于常规 bug 修复；不因普通修复递增次版本。
- 发布提交示例：`v5.0.8: 规范发布流程并清理退役代码`；脚本自动添加版本前缀，保留提交正文。
- Release 标题为 `v5.0.8 — AutoQuill`，正文首行为 `# v5.0.8`。
- 使用已配置的 Git 身份，中文和多行说明通过 UTF-8 文件传入。
- `main` 和本次 tag 原子推送，保留既有版本。目标 tag 已存在时停止并核对状态，不移动或覆盖已发布 tag。
- 每版只有 `AutoQuill-Setup-<版本>.exe` 和对应 `.exe.sha256` 两个上传资产。EXE 已压缩，不附备用安装 ZIP；GitHub 自动提供的源码 ZIP 不受影响。
- 发布说明放在 Release 正文，不另作上传资产；本机说明与产物在忽略的 `release/` 目录留档。

## 3. 根据改动选择验证

| 改动 | 发布前验证 |
|---|---|
| 文档或版本元数据 | 查看差异；文档调整本身通常只提交，用户要求发版时再构建 |
| 普通界面或独立模块 | 自动选择相关测试，检查改动 Python/JS 的语法 |
| 公共依赖、大范围重构或无法映射的运行时模块 | `--full-test`；未知运行时模块自动回退完整回归 |
| 下载、校验与更新编排 | 更新专项回归；下载通道变化时按需加 `--verify-download` |
| 安装器、冻结配置、启动器、退出或重启 | 生命周期专项回归和实际构建；有行为变化时做一次隔离安装演练 |

默认核对本地 SHA256、GitHub 对上传 EXE 计算的 digest/大小，并下载小型 SHA256 文件核对内容。完整安装包回下载和隔离旧版安装演练按改动追加。

main 的 Windows/Linux 完整 CI 在后台运行一次，tag 不重复触发。普通发布以资产校验通过为完成标志，报告当时 CI 状态；修改 CI 或修复其故障时，另确认首次运行结果。需要等待时一次等待后查看结论，避免频繁轮询。

`--skip-test` 仅复用当前改动已通过的测试和语法检查；`--skip-build` 仅复用版本与当前 HEAD 完全一致的构建。正常发布不使用跳过选项；变更后追加相关检查即可。

## 4. 失败恢复与结果报告

1. 根据阶段和日志定位失败。输出具体异常、版本和提交，不把测试夹具中的预期报错当作 CI 根因。
2. 修复后复用仍有效的结果，只重做失败或受新改动影响的步骤。
3. 已推送 tag 或已有 Release 时先查远端状态，保留已有版本；缺少的上传或校验步骤单独完成，避免整条流程重复执行。
4. 最终报告发布链接、安装包、提交、实际测试范围、阶段/总耗时和 CI 状态。未完成的检查如实注明。

v5.0.7 的统一发布命令基线为 **76.8 秒**：相关检查 7.5 秒、构建 44.0 秒、推送 6.1 秒、上传 10.2 秒、资产校验 3.0 秒。完整任务还包含准备与审核时间，比较时使用相同口径；网络与构建缓存会影响用时。

## 5. Release 说明写法

Release 面向使用者：陈述最终行为、具体症状与升级注意，不写开发对话或排查过程。CHANGELOG 保留维护者需要的详细记录，Release 从对应条目精简。

章节按 `Added`、`Changed`、`Fixed`、`Notes`、`Verification` 排列，有内容才写；安全修复存在时将 `Security` 置顶。例：

```markdown
# v<版本>

一句话说明本版变化。

## Changed

- 确认更新后自动完成下载、校验、安装和重启。

## Notes

- Windows 10/11（x64）；覆盖安装保留用户数据。
- 安装包未签名，SmartScreen 提示时选择「更多信息」→「仍要运行」。

## Verification

| 项目 | 结果 |
|---|---|
| 本地检查 | 填写本次实际范围与通过/跳过数量 |
| CI | 填写实际状态及运行链接 |
| 发布资产 | 填写实际 SHA256 与线上校验结果 |
```

验证结果使用本次实际数据。进行中的 CI 写“进行中”，尚未做的安装演练不写“通过”。
