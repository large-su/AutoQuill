## 1. 用户要的是什么（原话拆解）

一句话：**把「每天打开软件、挨个点按钮」变成「给 24 小时时间轴派任务，软件自己按点干活」**。

- 每天在**自己的知乎账号**上完成一串固定动作：从草稿箱发布若干篇、全链路写若干篇、
  打卡挑战、对收到的赞同/喜欢点感谢、挑一部分评论回复……
- 每个任务三要素：**怎么做**（执行方式）、**做多少**（数量配额）、**什么时候做**（时间点/时段）。
- 点「开始」后，软件自己看时间；到点执行；**冲突就排队**（不能两个任务抢浏览器）。
- 软件**关窗口≠退出**：像微信/QQ 一样驻留右下角托盘，随时点开看，自动化一直在后台挂着。
- 后台必须**轻、静默**：不抢焦点、不常驻浏览器、不干扰用户自己办公；重活到点才拉起。
- 用户的目标是**想干预时才进去看一眼**，其余时间交给系统（无人化管理）。

## 3. 核心模型（先把抽象定下来，后面才好长）

### 3.1 任务类型（TaskType）

每个类型声明自己的「执行契约」：

```
type            唯一标识（publish_drafts / full_chain / checkin / thank / reply_comment / refresh_snapshot）
params          参数（如 full_chain: {mode: classic|clean, rounds: 1}；thank: {batch: 7}）
daily_cap       每天最多执行几次 / 每次处理几条
window          允许执行的时段（如 09:00–23:00）
times           窗口内计划执行次数（如 3 次）
min_gap         两次之间的最小间隔（如 120 分钟）
jitter          时间抖动上限（默认 ±8 分钟，避免每天同一分钟机械执行）
requires        前置条件（登录有效 / 草稿数 ≥N / 前一个任务已完成）
success         成功判据（可验证的：服务端确认、页面状态、台账写入）
idempotent_key  幂等键（如 publish:2026-09-20:<qid>）——重启后绝不重复执行
dry_run         只演练不真做（首次启用默认开）
```

### 3.2 计划（Plan）与时间轴

用户配置存 `data/state/automation_plan.json`，示意：

```json
{
  "enabled": true,
  "window": {"start": "08:00", "end": "23:30"},
  "jitter_minutes": 8,
  "catch_up": "same_day",
  "daily_caps": {"publish_drafts": 3, "full_chain": 2, "checkin": 1,
                  "thank": 20, "reply_comment": 5, "refresh_snapshot": 2},
  "tasks": [
    {"type": "checkin", "at": "09:05"},
    {"type": "thank", "window": ["10:00", "22:00"], "times": 3,
     "min_gap_min": 180, "params": {"batch": 7}},
    {"type": "full_chain", "window": ["09:30", "21:00"], "times": 2,
     "min_gap_min": 240, "params": {"mode": "classic", "rounds": 1}},
    {"type": "publish_drafts", "window": ["10:00", "22:30"], "times": 3,
     "min_gap_min": 120, "params": {"source": "own_drafts_only": true}},
    {"type": "reply_comment", "window": ["12:00", "22:00"], "times": 2,
     "min_gap_min": 300, "params": {"batch": 3, "mode": "approve"}}
  ]
}
```

调度语义只有三种，覆盖所有诉求：**固定点**（打卡 09:05）、**窗口+次数+间隔**（发布 3 次/天、
每次间隔 ≥2h）、**依赖触发**（全链路写完 → 20 分钟后发布其中 1 篇）。

#### 「窗口 + 次数 + 间隔」到底怎么排（2026-09-19 按用户口径重做）

- **要的是「铺开」，不是「发一个等一小时」**：把时段等分成 N 份，每份随机取一点，再统一修复到
  两两间隔 ≥ 最小间隔（`automation/planner.py::spread_times`：分层随机 + 正向推/回推修复）。
  旧的「从起点累加随机间隔」是随机游走——3 篇会全挤在上午，后半天一个都不动。
- **间隔是下限**：任何相邻两个动作都 ≥ 最小间隔；不是「每次加一个随机间隔」。
- **数量上限是算出来的**：N 个动作之间只有 N-1 个间隔，`(N-1) × 间隔 ≤ 时段长度`，
  即 `N ≤ floor(时段 ÷ 间隔) + 1`。例：08:00–23:30 = 930 分钟、间隔 60 分钟 → 上限 16 个。
  设多了不会硬排：按上限排 + 时间轴上留一条「排不下」的说明（写明时段/间隔/上限与调整建议）。
- **续做**：今天已完成的部分不重排；剩下的在「最后一篇之后 → 时段末端」这段里重新铺开。

### 3.3 作业（Job）与台账

- `data/state/automation.jsonl`：每次作业一行（计划时间 / 实际开始结束 / 结果 / 产物 / 失败原因 /
  是否 dry-run）——**无人化必须可解释**：任何「说好该做却没做」都能查到原因。
- `data/state/automation_counters/<date>.json`：当天各类已用配额（跨重启保留）。
- 队列状态在内存（重启后由 plan + counters + 台账重建「今天还剩什么」）。

## 4. 时间轴、冲突与「错过怎么办」

1. **冲突**：同一时间只能有一个任务用浏览器（共享 profile 硬约束）→ 队列串行；
   UI 显示「排队中：前面还有 1 个（全链路撰写）」。手动操作**优先**：你在用的任务跑起来时，
   调度器不再派新任务；可选「打断当前自动化任务」。
2. **抖动**：所有触发点 ±jitter，且同类任务不固定在同一分钟；避免机械节律（也降低风控观感）。
3. **错过补做（catch-up）**：电脑关机/软件没开导致错过时间点 → 三选一：
   `none` 不补 / `same_day` 当日内找空档补（建议默认，且不突破配额）/ `next_window` 下个窗口补。
4. **幂等**：作业 key 唯一（含日期 + 目标对象），重启/重试都不会重复发布或重复感谢。
5. **熔断**：同类任务连续失败 N 次（默认 3）→ 暂停该类任务、托盘通知、台账记原因；
   登录失效/验证码/异常页 → 立即暂停全部自动化并通知（等人处理）。

## 6. 后台常驻（托盘）与「静默」

- **关窗 = 驻留托盘（M4 已落地）**：pywebview 的 WinForms 后端 + .NET `NotifyIcon`。
  spike（`tools/archive/probes/spike_tray.py`）先证明三件事，再改生产代码：
  ① NotifyIcon 必须由**消息循环所在线程**创建（`form.Invoke(Action(...))`），否则菜单点了没反应；
  ② `window.events.closing` 返回 False 即取消关闭 → 窗口 Hide()、`webview.start` 不返回，服务与
  调度器都还活着；③ 托盘菜单回调在 UI 线程，HTTP 请求要丢子线程。
  菜单：打开控制台 / 状态行 / 暂停·恢复 / 立即执行下一个 / 退出；关窗行为可在设置页切换
  （默认驻留托盘）；开机自启默认关闭，开启后以 `--tray` 静默驻留。
  ★ 退化路径：托盘图标建不起来时**自动按真关闭处理**——没有图标还隐藏窗口，用户就再也找不回来了。
- **资源占用**：调度器 tick 只做时间比较 + 读内存/小 JSON（CPU 近乎 0）；
  **浏览器按需拉起、任务结束即关**（现有任务本来就这样）——不会常驻一个浏览器占内存；
  重任务（撰写/发布）才短时占用网络与 CPU。
- **不抢焦点**：所有自动化浏览器一律 headless（沿用工作模式），不弹窗、不置顶。
- **开机自启**：安装器加一个可选任务项（默认关闭，设置里开关）。
- **睡眠/关机**：不安装系统服务、不唤醒机器；醒来后按 catch-up 策略处理并记台账。
- **退出保护**：正在执行任务时点「退出」→ 提示「当前任务 X 正在执行，等它做完再退 / 强制退出」。

## 7. 观察与控制（无人化不等于黑箱）

- **自动化模块**（左侧第 5 个模式）：
  - 顶部：总开关（开始/暂停）、今日进度（9/14 项）、下次执行倒计时、登录态、队列。
  - **24 小时时间轴**：横向时间轴 + 任务块（灰=未到点 / 蓝=进行中 / 绿=完成 / 黄=跳过 / 红=失败），
    点块看详情、产物链接、失败原因。
  - **任务清单**：每类任务的开关、每日配额、时段、间隔、批量大小（可编辑、即改即生效）。
  - **待批准**：评论回复等需要人过目的产出，一键批准/改后发/丢弃。
  - **历史**：按日/按类型查台账（成功、失败、跳过与原因）。
- **通知**：托盘气泡 + 窗口 toast（完成/失败/**需要你**：登录失效、验证码、发布失败）。
- **首次启用 = dry-run**：连续跑 1 天只记录「本应做什么」，你确认行为符合预期后再真开。

## 8. 风险与边界（必须写清楚）

1. **账号风控**：互动类（感谢/回复）最敏感 → 低配额 + 长间隔 + 时段限制 + 抖动；一天内动作总量设全局上限。
2. **发布不可逆**：草稿一旦发布即公开 → 默认只发布「本软件生成且通过质量闸门」的草稿；
   首次发布前托盘提醒（可在设置里关）。
3. **以你的身份说话**：评论回复默认「待批准」；如果选自动，需要先明确语气/长度/禁区（如不承诺、不引战、不涉政）。
4. **规则边界**：不做多账号、不做点赞/关注刷量、不做任何平台明令禁止的行为（既危险也不可持续）。
5. **不可控因素**：知乎改版、验证码、异地登录都会打断自动化 → 设计上「失败即暂停 + 通知」，不硬闯。

### M2 落地后的已知取舍（待确认）

- **「只发我们自己生成的草稿」暂时做不到**：现有本地数据（`output/*.md` 故事正文、
  `data/stories/**`、`data/state/published_topics.jsonl`）里都没有记录「这篇故事写进了哪个问题
  的草稿箱」，`published_topics.jsonl` 记的是**已发布**的问题。因此 M2 当前口径是
  **「发草稿箱里最旧的一篇」**（对应 `TASK_TYPES["publish_drafts"]["params"]["source"] = "all"`）。
  要做成「只发自己生成的」，需要新增一份**草稿台账**：在 `publish_story()` 确认服务端草稿落盘后
  追加 `{qid, title, question_url, time, md_path}` 到 `data/state/draft_ledger.jsonl`，
  `publish_draft(source="own")` 再按台账过滤（台账为空就什么都不发，而不是误发）。
  ★ 代价：升级后**旧版本写的草稿不在台账里**，默认切成 own 会导致「一篇都发不出去」，
  所以切换前要么补录台账（可按草稿箱卡片人工勾一遍），要么明确接受 all 口径。

## 11. 与现有架构的关系（避免长歪）

- 新增 `automation/` 作为独立包（Layer 2/3），**只编排、不直接操作 DOM**：DOM 动作仍归
  `applications/zhihu_story/`（新增 `browser_interact.py` 承载感谢/回复/打卡），工作流仍归 `workflows/`。
- 调度器不认识「知乎」，只认识任务类型与能力接口 → 未来加别的平台/别的任务不用改调度。
- 所有浏览器动作走 `browser_tasks.browser_busy()` 互斥；自动化与手动操作共用一套排队规则。
- 纯逻辑（planner/scheduler/store）必须可单测（时间可注入、抖动可注入种子），
  DOM 部分沿用现有 probe 真机校准约定。
