# 演进记录模块：第一代设计与使用

| 项目 | 内容 |
|---|---|
| **适用版本** | v5.1.0 起 |
| **最后更新** | 2026-10-02 |
| **状态** | 活跃 |
| **说明** | 记录软件改动与写作方案，按文章年龄观察多数作品是否稳定改善 |

## 目标与第一代范围

用户优先选择多数作品稳定改善的方案。中位数与 P25（较低四分位数）是主要观察值；篇均、最大单篇占比和作品分布帮助解释结果。少数爆款仍保留，但不会单独触发「方案变好」的结论。

第一代提供控制台的「演进记录」入口、写作方案与每次 Release 两种视图、节点详情、已公开作品归属确认、7/14/30/90 天观测，以及实际作品的赞同分布。图中的箭头表示改动顺序；反馈由作品记录计算，持续归回原方案。

首次起步历史来自当前分支可达的最近 16 个版本 tag；初始化后固定这一起点，后续版本按发布继续追加，本版追加 v5.1.0。使用相邻 tag 之间的完整改动区间，避免把安装器版本同步提交误当作一次版本的全部工作。发布历史随统一发布入口离线更新，安装版不依赖 Git、GitHub 登录或网络读取。

本版本在提交前生成准备记录，提交 SHA 留空。安装包读取已有的 `build_info.json` 补充实际构建来源提交，避免把上一版 HEAD 错写为新版本提交；下一次生成历史时再用已存在的 tag 记录替换。

第一代展示顺序演进，后续再补主动实验分支、合并、按天聚合、账号同期基线与试验规划。当前不自动修改生成策略、不训练 reward 模型、不宣布因果提升。

## 节点与记录

### 历史代码方案

相邻版本的写作代码指纹相同时，归并为同一个历史方案阶段；切换后又恢复相同代码，也形成新的阶段。首次窗口的改动区间以紧邻的更早 tag 为基线。

第一代代码指纹覆盖 `story_prompt.py`、`story_generation.py`、`config/story.py`、`applications/zhihu_story/prompts.py`、`workflows/workflow_generation.py`，统一 CRLF/LF 换行后计算。它用于识别这几份文件的变化，不代表已经完整识别一切会影响写作的行为。模型、作者风格、外部素材及当时运行配置缺失时，界面注明「历史运行配置未知」。文件哈希变化也不等同于能力变化。

工程修复可保持在同一写作代码方案中，每次 Release 仍可单独展开。历史版本号不能替代真实生成配置；同一天的多个版本不能仅凭日期给作品分配归属。

### 新稿件与试用阶段

稿件保存时记录内容哈希、文件名、应用版本与明确允许的模型/写作配置。第一代捕获点是文件保存时，尚不保证整个生成过程中配置始终一致；下一阶段可将捕获点前移到生成开始，并记录实际回退使用的模型、提示词及风格资料指纹。

连续使用相同快照归入同一试用阶段。方案切换后再恢复，建立新阶段。配置记录通过白名单选取，不写入 API Key、登录态、完整故事正文或完整配置对象。

保存草稿、收到发布回执、在公开内容快照中看到作品，分别记录。草稿不参与读者反馈评价。发布成功回执仅在明确的回答 URL 和唯一草稿关联下提供归属线索；公开快照及实际发布日期决定是否可观察。

## 历史作品归属

现有 `published_topics.jsonl` 的写入时间可能是草稿保存时间；它的 `version` 不能直接作为完整生成方案证明。旧性能台账会将缺失指标转成 0，因此演进模块不直接把它当作完整、精确的观测来源。

读取本机已公开作品快照作为起步样本，保留其数据来源与观测日期。能够用明确回答 ID 和台账版本提出建议时，仍标为待确认。标题相同、日期相近，不自动确认归属。

使用者可在「作品与反馈」中选择方案并点击「确认归属」，也可以选「暂不关联」后确认以撤销。该动作只修改本机分析记录，不改变知乎内容。人工关联历史方案后，当时运行配置缺失的提示仍保留。

确认归属时留存已知的历史观测；之后清理看板快照不会从方案统计中自动删除低表现样本。

## 观察口径

文章年龄从平台公开发布日期开始计算，不从草稿保存日期或版本发布日期开始计算。第一代使用日粒度；无年份的发布时间根据对应快照的观测年份归一，不能用今天的年份回填旧快照。

| 目标日 | 观察用途 |
|---|---|
| 7 天 | 早期启动 |
| 14 天 | 覆盖几天后开始起量的情况 |
| 30 天 | 阶段成绩，默认视图 |
| 90 天 | 长期表现，保留后续全部观测 |

只使用目标日到目标日 + 3 天内最接近目标日的有效实测数据；这是采样容差，不是知乎规则。例如只有第 60 天快照时，第 30 天成绩仍是「缺少窗口观测」。同龄日有多次观测时优先采用该日最新的有效值。

新抓取的缺失或无法解析指标保存为 `null`，真实的 0 保留为 0。旧归一化快照中的 0 可能来自解析失败，需保留不确定性。没有样本、尚未到观察日、已到观察日但缺少实测值，各自呈现，不统一计为零分。

方案统计包含已确认归属的公开作品数、已到观察日的作品数、实际有效观测数、赞同中位数、P25、篇均和最大单篇贡献比例。小样本显示观察结果及样本数，不给出胜负。长期新增反馈持续留在生成该作品的方案下。

第一代没有综合 reward 分数。下一阶段可加入同期同题材基线、点赞/阅读与收藏/阅读比例、启动时长、14～30/30～90 天新增反馈。评论数量不直接作为正向质量分。

## 文件与接口

| 文件 | 职责 |
|---|---|
| `core/evolution.py` | 本机方案、作品归属与反馈观察；计算视图数据 |
| `core/evolution_history.json` | 可打包的近期历史，只包含版本和代码元数据 |
| `tools/evolution_history.py` | 从本机 Git 生成近期历史，统一发布入口调用 |
| `webui/evolution_api.py` | 读取视图与确认归属 |
| `webui/static/evolution.js` / `evolution.css` | 图、节点详情、分布与作品列表 |
| `data/state/evolution.json` | 用户本机分析记录，排除版本跟踪与安装包 |

界面读取 `GET /api/evolution?horizon=30`，归属确认使用 `POST /api/evolution/assign`，请求体为 `{"aid":"回答ID","node_id":"方案ID"}`；撤销时 `node_id` 为 `null`。

「刷新本地记录」只读取本机结果；读者数据沿用「已发布内容看板 → 从知乎刷新」。不额外启动浏览器或重复抓取。外部反馈抓取成功后同步新增观测，未成功的抓取不覆盖上一份记录。

记录故障不应阻断原有生成或发布；记录损坏应报告异常，写入不能静默覆盖损坏文件。用户数据通过 `core.paths.data` 保存，只读历史通过 `core.paths.program` 加载。安装器将历史 JSON 与独立前端文件打包。

## 验收与下一步

第一代验收关注：近期真实历史可离线查看；工程版本合理归并；作品归属可确认和撤销；草稿不评分；无样本不等于零；错过窗口不伪造历史成绩；爆款不掩盖中位数；重启与后续版本不会转移旧作品反馈；记录不包含密钥或故事全文。

专项验证：`python -m unittest tests.test_evolution tests.test_evolution_history`。路由、生成、草稿发布及看板集成按对应测试补充。Windows 下设置 `AQ_UI_TESTS=1` 后运行 `python -m unittest tests.test_evolution_ui`，用隔离数据验证实际界面的视图切换、选择、关联、撤销和图表；不访问知乎，也不发布内容。通过后再按 [发布规范](RELEASE-GUIDE.md) 发版。

后续优先完善生成起始快照和稿件编辑追踪，再积累足够的 30/90 天实测样本。分支探索、同期交错试用及基线比较，在这些记录可靠后逐步加入。
