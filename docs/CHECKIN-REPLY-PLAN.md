## 1. 真机探针结论（今天实测）

### 1.1 打卡挑战页长什么样

- **当期活动**：创作打卡挑战赛第五十三期
- **URL**：`https://www.zhihu.com/parker/campaign/2083977679355889635?zh_hide_nav_bar=true`
- **每日成功判据（页面原文）**：完成「1 个以上」创作任务及「3 个以上」互动任务
- **今日任务实测状态**：

| 分组 | 任务 | 要求 | 今天的状态 |
|---|---|---|---|
| 创作 | 发布 1 篇回答 | ≥100 字 | ✅ 已完成（我们自动化发的） |
| 创作 | 发布 1 条想法 | ≥30 字 | 去发布 |
| 互动 | 关注 1 位知友 | — | ✅ 已完成（今天你手动做的） |
| 互动 | 发布 1 个问题 | 标题≥10字+描述 | 去提问 |
| 互动 | 发布 1 条评论 | **≥10 字**有效评论 | 去评论 |
| 互动 | 收听 Morning Call | ≥30 秒 | 去收听 |
| 互动 | 送出 1 个赞同 | 打卡当天 1 个 | ✅ 已完成（今天你手动做的） |

  内含 `.tasktree-task-title`（标题）、`.tasktree-desc`（说明）、
  `div.tasktree-btn > span.tasktree-btn-text`（按钮文案：`已完成` 或 `去发布/去提问/去评论/去收听`）。
  分组容器是 `div.tasktree-item-top`，解析时要过滤掉。

### 1.2 「每月换一期、换网址」有解

- `https://www.zhihu.com/creator`（创作中心首页）里有 **去打卡** 链接，href 直接指向当期 campaign。
- 所以**不需要你每期手工换 URL**：优先用缓存里的 URL；每期首跑或 URL 失效时，
  打开创作中心首页抓「去打卡」链接，自动更新缓存（一个函数的事）。
- `https://www.zhihu.com/parker` 是 404，不能当入口。

### 1.3 评论管理页（你给的那个网址）

- URL：`https://www.zhihu.com/creator/manage/comment/answer`
- 卡片：`div.CommentManage-CommentCard`，一屏实测抓到 **20 张**，滚动可继续加载。
- 单张卡片可读字段（全部实测有值）：
  - 评论者：`a.UserLink-link` 文本 + `/people/xxx` 主页链接
  - 被评论的回答：`a[href*=/answer/]`（同时带回答标题文本）
  - 时间：形如 `09-26 13:32`
  - 评论正文：`.CommentRichText` 内的 `span.RichText`
  - 操作按钮：**喜欢 / 回复 / 推荐**
- 最近 7 天的评论里，既有「被抢走的提成得上百万了吧，不走劳动仲裁？」这种可以友善回应的，
  也有「贱出天际」「莫名其妙」「看不下去」「作者你自己真的能看得懂吗？」这类戾气评论——
  **正好印证你说的筛选环节必须有**。

### 1.4 回答页的「关注 / 赞同」按钮

- 关注：`button.FollowButton`，三态文案：`关注` / `已关注` / `互相关注`
- 赞同：`button.VoteButton`（文案形如 `赞同 584`）——**打卡要的是「赞同」，不是「喜欢」**，
  你口语里的「点赞」我按「赞同」实现（页面原文是「送出 1 个赞同」）。
- 作者：`a[href*=/people/]`，作者名在同级链接文本里。

### 1.5 一个关键事实：互动任务一共 5 项，只要做满 3 项

页面上的互动任务池是：关注知友 / 发布问题 / 发布评论 / 收听 Morning Call / 送出赞同。
你选的 **关注 + 赞同 + 评论** 正好是 3 项，**刚好达标**，不需要碰「提问」和「收听」。

## 2. 我对你思路的理解（复述，请确认）

**A. 打卡互动（关注 + 赞同）不单独开任务，搭在「写草稿」的顺风车上。**
因为写草稿本来就要打开问题页、读参考回答——那一刻作者的「关注」按钮和「赞同」按钮就在眼前，
顺手点一下，零额外导航、零额外风控暴露。

**B. 三条判定规则：**
1. 这个知友已经关注过、这篇回答已经赞同过 → 跳过，换下一个草稿的参考回答再试；
2. 一整天遇到的都已经是关注过 / 赞同过的 → 不重复操作（说明今天这项多半已经达成）；
3. 到了当天最后一个「写草稿」仍没找到可关注 / 可赞同的目标 → **对最后一个目标做翻转**：
   取关再关注（你可能遇到确认弹窗，所以要连点两次）、取消赞同再赞同；
   **两项互不绑定**——谁先完成就收工，不要求在同一篇回答里。

**C. 评论回复每天只做 1 条，来源是评论管理页最近 7 天。**
先挑最友善的那条（戾气大的直接丢掉），读回我们当时的题目+回答，
再交给网页端大模型组织回复；用完删会话。

**D. 回复的四条硬要求：**
1. 有人味、不能有 AI 味；
2. 长度匹配对方（对方 2 个字就回短句，宁可更短）；
3. 不用对方用户名，只用「您 / 你」；
4. 友善、不硬刚、不说难听话；对方提建议就认真接住。

**E. 我的活儿**：写提示词、搭工作流、复用现有积累（DOM 通道、网页版大模型驱动、
自动化调度器、台账、AI 味检测器）。

如果以上理解有偏差，先纠正我，别让我按错的做。

## 3. 方案总览

一句话：**在现有自动化里加两条链路——「打卡互动」搭写草稿的顺风车，「评论回复」做独立任务，
两者合力把当日打卡从 2/3 推到 3/3；创作任务继续由现有的发布草稿承担。**

分工表（对应页面上的任务项）：

| 打卡任务项 | 由谁完成 | 什么时候 |
|---|---|---|
| 发布 1 篇回答（创作） | 现有 `publish_drafts`（已上线） | 已按排班自动发 |
| 关注 1 位知友（互动） | **新增：写草稿时顺带关注**（主）+ 打卡巡检兜底 | 当天第一次写草稿 |
| 送出 1 个赞同（互动） | **新增：写草稿时顺带赞同**（主）+ 打卡巡检兜底 | 当天第一次写草稿 |
| 发布 1 条评论（互动） | **新增 `reply_comment` 任务** | 每天 1 条，白天时段 |

## 4. 链路 A：打卡互动（关注 + 赞同）

### 4.1 时机

挂钩点：`workflows/base.py` 的 `run_single` / `run_clean`——**提取成功后、开始生成前**。
此刻我们已经知道最终选中的问题 URL；`browser.open_question(url)` 是幂等的（同页不重载），
首答作者的关注按钮与赞同按钮就在 DOM 里。

### 4.2 每天只读一次打卡页（状态权威口径）

当天第一次写草稿时，先打开当期打卡页，解析「今日任务」状态，落盘成当日快照
`data/state/checkin.json`。之后当天所有判断都读这份快照 + 本地台账，不再反复开页面。

好处：**你手动点过的（像今天这样），我一眼就知道，绝不重复操作。**

### 4.3 单次写草稿里的判定流程

```
需要关注？ = 打卡页「关注 1 位知友」未完成 且 今天还没成功关注过
需要赞同？ = 打卡页「送出 1 个赞同」未完成 且 今天还没成功赞同过
两者都不需要 → 整段跳过（零额外导航，行为与现在完全一致）

需要时：
  切到选中的问题页 → 读首答作者与两个按钮的状态
  需要关注：
      按钮是「关注」     → 点 → 校验变「已关注」→ 记台账 follow=done
      按钮是「已关注/互相关注」→ 记 tried（已关注，换下一个草稿）
  需要赞同：
      按钮未赞同         → 点 → 校验变为已赞同 → 记台账 vote=done
      按钮已赞同         → 记 tried（已赞同，换下一个草稿）
  如果「今天是当天最后一个写草稿」且某项仍未完成 → 对当前目标做翻转：
      关注：点「已关注」→ 出现「取消关注」（可能带确认弹窗，按你说的连点两次）→ 再点「关注」
      赞同：点「已赞同」取消 → 再点「赞同」
```

「当天最后一个写草稿」怎么知道：排班器给当天最后一个 `full_chain` 作业打标记
（`params.is_last_of_day = true`），执行器把它连同打卡上下文一起传给工作流。

### 4.4 兜底：`checkin` 巡检任务（建议要有）

主路径有天然盲区：当天一篇草稿都没写成功、或最后一班被跳过，翻转就没机会做。
所以再加一个轻量任务类型 `checkin`（默认 1 次/天，建议排在 21:30 前后）：

1. 打开当期打卡页 → 刷新当日快照（顺带把「今天打卡成没成」写进通知）；
2. 若关注 / 赞同仍未完成 → 打开推荐问题页取首答，执行关注 / 赞同（必要时走翻转）；
3. 若评论任务仍未完成 → 交给 `reply_comment` 补做（或直接报告需要人工）。

它同时是**当日打卡的可视化数据源**：时间轴上能直接看到「创作 √ / 互动 3/3」。

## 5. 链路 B：评论回复（`reply_comment`）

### 5.1 流程（十步）

```
1  打开评论管理页，滚动采集卡片（目标 ≥20 条，够 7 天用）
2  解析：{评论者, 主页, 回答URL, 回答标题, 时间, 正文, 卡片定位}
3  过滤：7 天内 ∧ 未回复过（台账去重）∧ 非纯表情/单字 ∧ 非我们自己
4  规则预筛：命中戾气词表（恶心/垃圾/弱智/取关/举报/胡编/抄袭/什么玩意/看不下去…）→ 剔除或降权
5  候选排序 → 取前 K 条（≤10）交给筛选环节
6  【网页版大模型 · 第 1 轮】从候选里挑出最友善、最适合友善回应的一条 → 只回一个编号
7  打开该评论对应的回答页 → 读回「当时的题目 + 我们的回答正文」（截断到合理长度）
8  【网页版大模型 · 第 2 轮 · 同一会话】喂「对方评论 + 题目 + 回答 + 格式要求」→ 生成回复
9  本地校验：长度（≥10 且不超过对方 1.2 倍）、无用户名、AI 味检测（复用 core/detectors）
   → 不合格带原因重写（≤2 次，沿用项目里成熟的「带反馈重试」模式）
10 回评论页 → 定位该评论 → 点「回复」→ 填入 → 发送 → 校验落地
    → 写台账 data/state/comment_replies.jsonl → 删除网页会话（会话纪律）
    → 回读打卡页，确认「发布 1 条评论」是否真的计入
```

### 5.2 为什么是「两轮同一个会话」

项目已有的会话纪律是：**一条任务从头到尾只开一个网页会话，做完删除**。
所以筛选与写作放在同一个会话的两轮里，Task 结束 `reset_driver(delete_session=True)` 兜底清理。
筛选单独一轮而不是合并进写作，是为了**不让模型一边挑一边写**——
分开之后，「挑错人」和「写坏话」两种失败可以分别定位。

### 5.3 提示词草案（我会再打磨，这里给你看方向）

**提示词 1：挑最友善的一条**（只喂评论正文与编号，**不喂用户名**，避免身份偏见）

```
下面是最近 7 天读者在我知乎回答下的评论（编号 + 内容）。
我要挑出其中**最友善、最适合被友善回应**的一条来回复，只挑一条。

优先挑：真诚的夸奖、感谢、认真的提问、具体的建议（哪怕带着不同意见）。
直接排除：人身攻击、嘲讽挖苦、阴阳怪气、无端指责、纯情绪宣泄、纯表情、广告。
如果一条评论既有情绪又有信息量，按「能不能友善地接住」判断。

只输出那一条的编号，不要解释、不要标点、不要输出别的任何字。

评论列表：
1. …
2. …
```

**提示词 2：写回复**

```
你是在知乎写故事的人，现在要回复读者在自己回答下的评论。

【对方的评论】…
【我们当时的题目】…
【我们当时的回答（节选）】…

写作要求：
1. 说人话，像个真人随手回的，不要客服腔、不要总结腔、不要排比句；
   禁止出现「感谢您的认可」「希望对你有帮助」「首先/其次/总之」这类套话。
2. **长度跟着对方走**：对方越短你越短，最多不超过对方的 1.2 倍；
   但平台要求有效评论 ≥10 字，所以下限 10 字（对方只写两个字时，就用一句 10–15 字的口语）。
3. **不要提对方的名字**，称呼只用「您」或「你」。
4. 对方夸你 → 谢谢 + 一句自然的回应，别谦虚过头也别自夸；
   对方提问 → 直接答，答不上来就说没有细想过；
   对方提建议 → 认真接住，承认问题，说清会怎么改，**绝不辩解、绝不硬刚**；
   对方说看不下去 / 不喜欢 → 客气接住，不争论。
5. 不引战、不承诺、不谈敏感话题、不带任何平台外信息。

只输出回复正文本身：不要引号、不要署名、不要任何解释、不要 markdown。
```

长度档位（我会写进提示词，并做本地硬校验）：

| 对方评论字数 | 期望回复字数 |
|---|---|
| 2–4 字 | 10–15 字 |
| 5–15 字 | 10–20 字 |
| 16–40 字 | 15–45 字 |
| 40 字以上 | 30–60 字 |

### 5.4 幂等与去重

回复台账 `data/state/comment_replies.jsonl` 每条记：
`{回答URL, 评论者, 评论正文hash, 评论时间, 回复正文, 发送结果, 时间}`。
同一条评论**永不回复第二次**（重启、重试都不会重复）。

## 7. 风险与护栏

1. **账号风控**：每天净增动作只有「1 关注 + 1 赞同 + 1 评论」，全部走无头浏览器、
   时段内随机、失败不硬闯；出验证码 / 登录失效立刻暂停自动化并通知（沿用现有 NeedHuman 机制）。
2. **取关再关注是真实副作用**：先取关后关注之间存在一个短暂「未关注」窗口。
   护栏：① 只在当天最后一个草稿、且打卡还没达成时才做；② 关注回来必须校验成功，
   失败重试一次后**立即通知你**，并在台账里记成「需要人工」；③ 一天最多一次。
3. **回复内容以你的身份发出**：措辞风险最高，所以建议**先演练**（见决策点）。
4. **平台改版**：打卡页 / 评论页都是前端渲染，选择器会变。所有选择器走候选列表 + 失败时
   dump 现场（沿用现有 `_dump_page_state` 约定），改版时改一处即可。
5. **不做的边界**：不做多账号、不做批量点赞关注、不做刷量；
   「发布 1 个问题」「收听 Morning Call」不做（没必要，3 项已够）。

### 12.4 单次任务轴与详情卡（用户 2026-09-27 第二轮口径）

用户指出：打卡互动 / 回复评论是「一天一次」的任务，不该和「要做 N 次」的发布/写草稿挤在
同一条时间轴上（那条轴的语义是「把 N 个动作铺开、间隔 ≥1 小时」，单次任务没有这些属性）。
于是重新设计：

**① 主时间轴只留「要做 N 次」的任务**（发布草稿 / 全链路撰写）；
**② 新增「单次任务轴」**：一天一次的任务画成**点**而不是条，按**阶段**排序并用连线串起来
（① 回复评论 → ② 打卡检查）；
**③ 轴下方两张详情卡**：打卡卡（活动名 / 检查时间 / 三项达成情况 / 是自动化还是手动完成的 /
补做与跳过记录）、回复卡（抓取多少条 → 候选多少条 → 过滤了什么 / 今天回了哪几条、回复全文 / 演练还是已发送）。

**视觉分工（用户 2026-09-27 拍板）**：颜色**只表达状态**（沿用主时间轴那套：空心=未到点、
闪动=执行中、实心=完成、斜杠=跳过、感叹号=失败）；任务身份用**形状 + 编号 + 中文标签**表达：
◆ 菱形=回复/对话类、● 圆形=检查/巡检类、■ 方形=生成/写入类、▲ 三角=对外发布类。

**★ 阶段闸门（真正的防事故设计）**：
`planner.due_jobs` 新增阶段判定——阶段 2 的打卡检查**必须等阶段 1 的回复评论进入终态**才允许派发。
之前只看「到点没 + 优先级」，随机落点一旦把检查排在回复前面，检查就会抢跑、报告一个
「还没做完」的假象（用户指出的原话：「回复肯定要提前完成，打卡最终在晚上检查是否完成」）。
判据刻意宽松：**只要已结束，不要求成功**——回复失败/跳过也照样放行，否则回复一挂、检查也废了。
另配安全阀：前序作业还挂着未执行、但它的时段已经过去（今天不可能再跑）→ 放行，不把检查卡死一整天。
